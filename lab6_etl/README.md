# Технологии Программирования · Цели и задачи лабораторной работы

**Цель лабораторной работы** заключается в получении практических навыков построения ETL-пайплайна: загрузка данных из CSV, очистка и преобразование данных, агрегация, загрузка в базу данных SQLite и базовая визуализация результатов.

**В рамках выполнения лабораторной работы были поставлены следующие задачи:**

- Реализовать этап Extract: загрузка исходного CSV-файла с обработкой исключений и логированием метаданных датасета.
- Реализовать этап Transform: обнаружение и устранение дубликатов, пропусков и аномальных значений в данных.
- Реализовать этап Aggregate: группировка очищенных данных по категориям и периодам с расчётом ключевых бизнес-метрик.
- Реализовать этап Load: сохранение очищенных и агрегированных данных в базу данных SQLite через SQLAlchemy.
- Реализовать этап Visualize: построение аналитических графиков и сохранение их в файловую систему.
- Организовать полное логирование всех этапов пайплайна в файл и стандартный вывод.

# Технологии Программирования · Ход выполнения и описание этапов

Пайплайн реализован в виде класса `SalesETLPipeline` с методами `extract()`, `transform()`, `aggregate()`, `load_to_sqlite()`, `visualize()` и оркестрирующим методом `run()`. Логирование организовано двумя обработчиками: одновременно в файл `logs/etl.log` и в стандартный вывод консоли.

## Этап 1: Extract — Извлечение данных

Метод `extract()` загружает CSV-файл `sales.csv` в объект `pandas.DataFrame`. Перед загрузкой выполняется проверка существования файла; при его отсутствии или пустом содержимом генерируется исключение `FileNotFoundError` / `ValueError`.

Согласно записям `logs/etl.log`, исходный набор данных содержал **11 строк** и **9 колонок**:

```

  'product_name', 'category', 'quantity', 'price_per_unit',
```

**Схема исходного датасета:**

## Этап 2: Transform — Очистка и трансформация

Трансформация выполнялась над копией исходного DataFrame (`self.raw_data.copy()`), что исключало изменение объекта `raw_data`. В процессе выполнения было выявлено и устранено три класса проблем качества данных.

**Шаг 1. Удаление полных дубликатов.** Метод `df.drop_duplicates(inplace=True)` выявил **1 полностью задублированную строку**: заказ `order_id=1010` («Книга SQL», 2 шт., 2500 руб., Ольга Новикова, Москва) присутствовал в файле дважды. Одна из копий была удалена. После этого шага датасет составил **10 строк**.

**Шаг 2. Приведение типов данных.** До обработки пропусков выполнено принудительное приведение типов с флагом `errors='coerce'`: `quantity` и `price_per_unit` → `pd.to_numeric()`, `order_date` → `pd.to_datetime()`.

**Шаг 3. Обработка пропущенных значений.** Строка `order_id=1004` содержала пропуски в текстовых полях. Стратегия: **текстовые поля → `'Unknown'`**, **числовые поля → медиана** по соответствующей колонке.

**Шаг 4. Фильтрация аномальных значений.** Строка `order_id=1005` содержала `quantity = -1` (клавиатура). Условие `df[(df['quantity'] > 0) & (df['price_per_unit'] > 0)]` удалило **1 аномальную строку**.

**Шаг 5. Обогащение данных.** Добавлены расчётные поля:
- `total_amount` = `quantity × price_per_unit`
- `month_year` = `order_date.dt.strftime('%Y-%m')`

| Удаление аномалии | `order_id=1005`, `quantity=-1` | Строка удалена |

## Этап 3: Aggregate — Агрегация

Агрегация выполнялась методом `df.groupby(['category', 'month_year'])` с расчётом четырёх метрик:

| Метрика | Исходная колонка | Функция |
|---|---|---|
| `total_quantity` | `quantity` | `sum` |
| `total_revenue` | `total_amount` | `sum` |
| `avg_price` | `price_per_unit` | `mean` |
| `order_count` | `order_id` | `nunique` |

```

```

Три аналитические группы: «Электроника / 2024-01», «Книги / 2024-01» и «Unknown / 2024-01».

# Технологии Программирования · Теоретический базис для защиты работы

<details>
<summary><strong>Вопрос 1. Какие аномалии и пропуски были обнаружены в исходных данных? Как вы их обработали и почему?</strong></summary>

**Ответ:**

В исходном датасете (`sales.csv`, 11 строк) выявлено три класса проблем:

**1. Полный дубликат (1 строка).** Строка `order_id=1010` («Книга SQL», qty=2, price=2500) присутствовала дважды. При загрузке в аналитику повторная запись удвоила бы выручку. Решение: `drop_duplicates()` — детерминированное устранение полных копий.

**2. Строка с пропущенными значениями (`order_id=1004`).** Поля `product_name`, `category`, `customer_name`, `customer_city` отсутствовали; числовые данные были корректны. Стратегия: *текстовые поля* → `'Unknown'` (сохраняет транзакцию в датасете), *числовые поля* → медиана (устойчива к выбросам в отличие от среднего). Полное удаление строки было бы избыточным, так как финансовые данные корректны.

**3. Аномальное значение (`order_id=1005`).** Поле `quantity = -1` для клавиатуры является бизнес-невозможным. Строка удалена фильтром `df[df['quantity'] > 0]`, поскольку сохранение записи привело бы к отрицательному `total_amount` и искажению выручки.

</details>

<details>
<summary><strong>Вопрос 2. В чём разница между ETL и ELT? Какой подход применён в данной задаче?</strong></summary>

**Ответ:**

**ETL (Extract → Transform → Load)** — классическая архитектура, при которой данные трансформируются **до** загрузки в хранилище. Трансформация выполняется на промежуточном слое; в хранилище поступают уже чистые данные.

**ELT (Extract → Load → Transform)** — «сырые» данные загружаются в хранилище в исходном виде, а трансформация выполняется **внутри** него средствами SQL или dbt. Оправдан при наличии мощного облачного DWH (BigQuery, Snowflake).

| Критерий | ETL | ELT |
|---|---|---|
| Место трансформации | Промежуточный слой / память | Внутри целевого хранилища |
| Инструменты | pandas, Spark, Airflow | dbt, BigQuery SQL |
| Применимость | Малые/средние объёмы | Большие объёмы, облачные DWH |

В данной работе применён **подход ETL**: очистка и трансформация выполнялись в памяти через `pandas` до записи в SQLite.

</details>

<details>
<summary><strong>Вопрос 3. Почему в реальных проектах данные не загружают напрямую в базу без очистки?</strong></summary>

**Ответ:**

1. **Целостность данных:** Дубликаты (как `order_id=1010`) приведут к задвоению метрик в отчётах — выручка будет завышена.
2. **Корректность вычислений:** Аномальные значения (`quantity=-1`) дадут отрицательный `SUM(total_amount)`, что сделает финансовую отчётность недостоверной.
3. **Несоответствие типов:** Без приведения типов строковые представления дат останутся текстом, что сделает невозможным SQL-агрегацию.
4. **Пропагация ошибок:** «Грязные» данные становятся источником для производных таблиц, дашбордов и ML-моделей («Garbage In — Garbage Out»).
5. **Стоимость исправления:** По принципу «shift-left» стоимость исправления дефекта на этапе ETL в 10–100 раз ниже, чем после публикации отчётов.

</details>

<details>
<summary><strong>Вопрос 4. Какие ещё трансформации могли бы быть полезны для этих данных?</strong></summary>

**Ответ:**

1. **Нормализация регистра:** `.str.strip().str.title()` для `customer_name`, `customer_city` предотвращает ситуацию, когда «Москва» и «москва» считаются разными городами при группировке.
2. **Временные признаки:** Извлечение `day_of_week`, `week_number`, `quarter` из `order_date` для анализа сезонности.
3. **Сегментация заказов:** Признак `order_segment` («малый» < 5000 руб., «средний» 5000–30000 руб., «крупный» > 30000 руб.) для RFM-анализа.
4. **Стандартизация `payment_method`:** Проверка на допустимые значения через справочник исключит ошибки ввода («CARD», «Card»).
5. **Скользящая средняя выручки:** `rolling(window=3).mean()` для сглаживания флуктуаций и выявления тренда продаж.
6. **Геокодирование:** Обогащение координатами по `customer_city` для географической аналитики.

</details>
