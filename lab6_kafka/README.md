# Технологии Программирования · Ход выполнения и описание инфраструктуры

## 2.1 Инфраструктура: docker-compose.yml

Кластер Apache Kafka разворачивался локально средствами Docker Compose в среде WSL 2. Конфигурация включала три сервиса:

**Zookeeper** — сервис координации кластера, отвечающий за хранение метаданных брокеров, выборы лидеров партиций и управление конфигурацией. Экспонирован на порту **2181**.

**Kafka Broker** (`cp-kafka:7.5.0`) — основной брокер сообщений. В переменных окружения настроены `KAFKA_ADVERTISED_LISTENERS` с внутренним (`PLAINTEXT://kafka:9092`) и внешним (`PLAINTEXT_HOST://localhost:9092`) адресами. Порт **9092** использовался клиентами для подключения.

**Kafka UI** — веб-интерфейс для визуального мониторинга кластера в реальном времени. Доступен по адресу `http://localhost:8080`. Позволяет просматривать топики, содержимое партиций, смещения консюмерских групп и состояние брокера без CLI.

```yaml
version: '3.8'
services:
  zookeeper:
    image: confluentinc/cp-zookeeper:7.5.0
    ports:
      - "2181:2181"
  kafka:
    image: confluentinc/cp-kafka:7.5.0
    depends_on: [zookeeper]
    ports:
      - "9092:9092"
  kafka-ui:
    image: provectuslabs/kafka-ui:latest
    depends_on: [kafka]
    ports:
      - "8080:8080"
```

## 2.2 Продюсер (producer.py)

Продюсер инициализировался с параметрами подключения `bootstrap_servers=['localhost:9092']` и JSON-сериализатором:

```python
self.producer = KafkaProducer(
    bootstrap_servers=self.bootstrap_servers,
    value_serializer=lambda v: json.dumps(v, ensure_ascii=False).encode('utf-8'),
    key_serializer=lambda k: str(k).encode('utf-8')
)
```

**Автоматическое создание топика:** При первой отправке продюсер автоматически инициировал создание топика `"orders"` на брокере.

**Генерация сообщений:** Каждое сообщение — словарь с `order_id` на основе `uuid.uuid4()`, данными о клиенте, товаре, количестве и сумме.

**Партиционирование:** Сообщения отправлялись с ключом `key=str(order['customer']['id'])`. Kafka применяет хэш-партиционирование: `partition = hash(key) % num_partitions`. Это гарантирует, что **все заказы одного клиента попадут в одну партицию**, обеспечивая строгий порядок обработки его событий.

## 2.3 Консюмер (consumer.py)

Консюмер подключался к топику `"orders"` с тремя ключевыми параметрами:

```python
self.consumer = KafkaConsumer(
    self.topic,
    bootstrap_servers=self.bootstrap_servers,
    group_id='order_stats_group',
    auto_offset_reset='earliest',
    enable_auto_commit=True,
    value_deserializer=lambda v: json.loads(v.decode('utf-8'))
)
```

- **`group_id='order_stats_group'`** — принадлежность к консюмерской группе; Kafka хранит смещения отдельно для каждой группы.
- **`auto_offset_reset='earliest'`** — при первом подключении начинать чтение с первого сообщения в партиции (offset=0).
- **`enable_auto_commit=True`** — автоматическая фиксация смещения после обработки каждого сообщения.

**Логика агрегации:** Консюмер поддерживал в памяти счётчики `total_orders` и `total_revenue`, обновляемые при получении каждого сообщения.

**Итоговые результаты (20 обработанных заказов):**

| Метрика | Значение |
|---|---|
| Обработано заказов | 20 |
| Общая выручка | **971 000,00 руб.** |
| Средний чек | **48 550,00 руб.** |

# Технологии Программирования · Теоретический базис для защиты работы

<details>
<summary><strong>Вопрос 1. Что такое топик, партиция, оффсет в Kafka? Как они использовались в работе?</strong></summary>

**Ответ:**

**Топик (Topic)** — именованный логический канал, в который продюсеры публикуют, а консюмеры читают сообщения. В работе использовался топик **`"orders"`**, содержащий события о заказах.

**Партиция (Partition)** — физическое подразделение топика; каждая партиция — упорядоченный, неизменяемый лог записей. Обеспечивают параллелизм. В работе партиционирование по **ключу `customer_id`** гарантировало, что все заказы одного клиента попадают в одну партицию и обрабатываются в строгом порядке.

**Оффсет (Offset)** — уникальный монотонно возрастающий идентификатор каждого сообщения внутри партиции. Группа `order_stats_group` хранила свой committed offset на брокере. Параметр `auto_offset_reset='earliest'` указывал начинать с offset=0 при первом подключении.

</details>

<details>
<summary><strong>Вопрос 2. В чём разница между продюсером и консюмером? Зачем нужна группа консюмеров (group_id)?</strong></summary>

**Ответ:**

**Продюсер** — клиент, который **публикует** сообщения в топик. Несёт ответственность за сериализацию и выбор партиции через ключ.

**Консюмер** — клиент, который **читает** сообщения. Управляет оффсетом и обрабатывает данные по бизнес-логике. Продюсер и консюмер полностью **развязаны** (decoupled) и взаимодействуют только через брокер.

**Группа консюмеров (Consumer Group)** решает задачу горизонтального масштабирования:
- Каждая партиция в каждый момент назначена **только одному консюмеру** из группы.
- При добавлении нового консюмера Kafka автоматически перераспределяет партиции (rebalance).
- Разные группы с разными `group_id` читают одни сообщения **независимо** — каждая ведёт свой оффсет («fan-out»).

В работе использовалась группа `order_stats_group` — единственный консюмер получал все партиции топика `"orders"`.

</details>

<details>
<summary><strong>Вопрос 3. Какие преимущества даёт потоковая обработка перед пакетной (ETL из Части 1)?</strong></summary>

**Ответ:**

| Характеристика | ETL + SQLite (Часть 1) | Apache Kafka (Часть 2) |
|---|---|---|
| Задержка обработки | Минуты–часы | Миллисекунды–секунды |
| Актуальность данных | «Вчерашние» на момент анализа | Актуальны в момент события |
| Масштабируемость | Ограничена ресурсами машины | Горизонтальная (партиции + брокеры) |
| Отказоустойчивость | Зависит от файловой системы | Репликация между брокерами |
| Сложность инфраструктуры | Низкая (Python + SQLite) | Высокая (Kafka + Docker) |
| Повторная обработка | Перезапуск скрипта | Сброс оффсета консюмера |
| Типичный use case | Ночные отчёты, DWH | Fraud detection, мониторинг, рекомендации |

**Главное преимущество:** В Части 1 пайплайн обрабатывал статический файл; в Части 2 консюмер обновлял агрегаты немедленно при каждом новом заказе, что позволяет принимать оперативные решения без ожидания ночного ETL-прогона.

</details>

<details>
<summary><strong>Вопрос 4. Приведите 3 реальных сценария использования Kafka в бизнесе (не связанных с логированием).</strong></summary>

**Ответ:**

**Сценарий 1. Fraud Detection в банке.** Каждая транзакция публикуется в Kafka немедленно. ML-консюмер анализирует паттерн клиента (партиционирование по `customer_id`) и при аномалии публикует сигнал в топик `fraud-alerts` — карта блокируется за сотни миллисекунд.

**Сценарий 2. Персонализированные рекомендации в e-commerce.** Каждый клик, просмотр и добавление в корзину публикуются как события. Потоковый процессор обновляет профиль интересов пользователя и рекомендации на главной странице после каждого действия — в отличие от пакетного подхода, рекомендации актуальны за последние секунды.

**Сценарий 3. Синхронизация микросервисов в доставке.** Изменение статуса заказа («передан курьеру», «доставлен») публикуется в топик `order-status-updates`. Сервис уведомлений, аналитики и складского учёта читают его параллельно без жёсткой зависимости между собой.

</details>

<details>
<summary><strong>Вопрос 5. Что произойдёт, если запустить 2 консюмера с одинаковым group_id?</strong></summary>

**Ответ:**

Pri запуске второго консюмера с `group_id='order_stats_group'` Kafka инициирует **перебалансировку (Rebalance)**:

1. Group Coordinator обнаруживает нового члена группы.
2. Все консюмеры приостанавливают потребление.
3. Партиции топика перераспределяются между консюмерами.
4. **Каждое сообщение обрабатывается ровно одним консюмером** — дублирования нет.

**Практический результат:** Если топик `"orders"` создан с 1 партицией, второй консюмер окажется **idle** — не получит ни одной партиции. Для полноценного параллелизма число партиций должно быть ≥ числа консюмеров (`--alter --partitions 2`).

**Важное следствие:** Счётчики `total_revenue` в памяти каждого консюмера будут содержать **частичные** агрегаты. Для глобальных метрик необходимо хранить состояние во внешнем хранилище (Redis) или использовать Kafka Streams.

</details>
